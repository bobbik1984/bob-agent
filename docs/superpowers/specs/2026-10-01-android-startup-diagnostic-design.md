# Android 启动卡屏诊断包设计（2026-10-01）

## 目标与已知事实

Pixel 8 上已安装的 Bob v0.9.21 在黑底蓝字 Logo 短暂出现后停在白底蓝 Logo。ADB 确认进程与 WebView 渲染进程仍在，Android 系统启动页已退出；当前 APK 与本地归档文件哈希一致，但它不可调试。现有日志不足以判断 Vue 初始化、WebView 资源加载、Tauri 桥接或 Rust 后台任务哪一段停滞。

目标是制作**一次性 Android 诊断 APK**，在不清除既有安装数据的前提下定位首次未完成的启动阶段。此工作不代表 A4 真机验收通过，也不改变正式包的安全边界。

## 方案选择

1. **隔离云端构建（采用）**：在诊断分支上加入最小启动探针和专用云端工作流，复用 GitHub Actions 中已有的 Android SDK 与签名 Secret；上传可下载的构建产物。避免将诊断开关合入正式主线。用户已允许推送云端构建，包括构建可能产生的发布记录。
2. 本机补装 SDK/JDK 并提供签名材料：能本地迭代，但当前机器缺少工具与 keystore，增加凭据分发及环境变动，不采用。
3. 只继续看正式包的 ADB 日志：无 WebView 调试入口，已无法区分静态 Logo 后的前端阶段，不采用。

## 实现边界

- 诊断包与正式版保持相同 applicationId 和签名；不更改数据库结构、配对数据、模型配置、网络端点或故障注入 Profile。
- 探针在 HTML 最早执行点、前端入口加载前后、Vue 挂载前后以及 `window.error` / `unhandledrejection` 输出**不含用户内容与凭据**的阶段标识和错误类型；超时记录当前阶段，不自动清除 Logo 来掩盖故障。
- 仅诊断构建开启 Android WebView 调试；正式工作流和正式构建不打开该能力。
- 诊断流水线须提供精确提交 SHA、APK SHA-256、签名校验结果与构建日志。不得自动执行官网部署或替换用户的正式下载入口。
- 安装前比较诊断 APK 与已装 Bob 的签名证书。若无法核实一致，或 Android 覆盖安装拒绝，立即停止；**禁止卸载、清除数据或降级绕过**。
- 真机运行时先清空 Logcat 缓冲区（不触碰应用数据），冷启动 Bob，采集带时间戳的启动日志、WebView 错误及屏幕状态。日志对 token、URL 查询参数和用户消息脱敏后再留证。

## 验收判据

1. 诊断 APK 可由云端成功构建、签名并下载，且其证书与手机现有安装一致；覆盖安装后 Bob 数据仍在。
2. 每次冷启动都能观察到有序阶段标识，或者明确记录停在第一个未达阶段及对应异常；不把单纯“进程仍在”当作启动成功。
3. 若诊断包可打开 WebView 调试，能读取控制台/网络失败原因；若调试连接不可用，阶段日志仍足够把问题缩小到 HTML、前端入口、Vue 挂载或原生桥接中的一段。
4. 对根因形成可复现证据并提出最小修复；诊断分支不直接成为正式发版或 A4 验收依据。

## 失败与停止条件

云端签名 Secret 不可用、工作流失败、证书不一致、Android 拒绝覆盖安装、日志出现敏感信息风险时停止后续安装或采集，并报告已经验证的事实与下一步选择。任何情况下均不清除手机上的 Bob 数据。
