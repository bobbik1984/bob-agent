# Bob 双端统一版本与受控发布设计（2026-10-01）

## 决策与适用范围

Bob 仍是同一套产品源码，Windows 与 Android 的同一候选批次必须来自同一 Git 提交，并显示同一应用版本。版本一致只证明构建来源对应，不代替协议兼容、配对或远程执行验收。本设计适用于 `mobile-pc-rebuild` 施工线，不把旧 v0.9.16～v0.9.21 功能整体并回，也不立即发布或覆盖现有稳定下载入口。

采用根目录 `package.json` 的 `version` 作为唯一人工编辑的版本源。构建前由确定性检查核对主应用 Tauri/Cargo、安装器 package/Tauri/Cargo、相关 lockfile 的根包版本；不一致立即失败。安装器属于同批次产品，不能继续停留在 0.9.7。同步工具可以从根版本更新这些派生元数据，但 CI 必须先检查已提交文件一致性，不允许在构建中悄悄改版本并继续出包。Android `versionCode` 必须随版本单调递增，不允许使用低于手机已装版本的包进行覆盖安装。

## 构建与发布状态

1. **开发中**：本地测试和代码审查，不产生对外安装包。
2. **双端候选**：将同一提交推至受控施工分支；Windows 和 Android GitHub Actions 都运行版本一致性检查并构建。各自产物作为标注版本与完整提交 SHA 的 CI Artifact 保存；候选分支不写 GitHub Release，也不更新官网固定下载文件。
3. **双端验收**：核对 PC 安装器和签名 APK 的版本、提交 SHA、哈希、Android 签名，并分别验证桌面启动与手机启动；手机→PC 的配对及只读指令需独立真机验收。任一端失败，整批次不晋级，不能用另一端成功替代。
4. **显式晋级**：只有用户确认对应验收门槛后，才从已验证的同一 SHA 产物创建版本化 GitHub Release，并按现有管理流程同步官网/下载中心。不得因推送施工分支或单端成功自动覆盖 `latest-desktop`、`latest-mobile` 或官网稳定入口。晋级动作须验证两个产物齐备、版本与 SHA 一致，再变更公开指针；失败时保留旧稳定入口。

## 版本推进规则

当前 Pixel 8 已安装 0.9.22 候选 APK。0.9.23 仅作为本地已核验但未安装的前向恢复包使用，不把它当作新的功能里程碑。现有 0.9.22 源码中的 PC 安装器元数据应先对齐 0.9.22，但此举本身不构成 PC 功能更新或安装建议。下一次包含双端功能改进、供两端一起安装的候选批次从高于 0.9.23 的新版本号开始；不得让同一个公开版本号指向两个不同的提交或二进制。

## 组件职责与失败处理

- 版本校验工具只读取根版本及派生清单，报告不一致的具体文件；不访问网络、不改用户数据。版本同步是显式开发步骤，完成后必须提交所有派生文件。
- Android CI 负责官方签名 APK 及签名/版本校验；Windows CI 负责主应用载荷、独立安装器及便携包。两条流水线都从同一提交检出，不互相复制旧产物。
- 候选产物的文件名包含版本；证据同时记录完整 Git SHA 和 SHA-256。`latest` 类型名字仅在正式晋级后更新，不能在候选阶段造成“最新版”误导。
- 任何版本不一致、缺失签名、单端构建失败、产物 SHA 对不上或真机验收失败，都阻止发布。保留已验证的旧稳定下载入口与本地恢复包，不进行卸载、数据清除或强制降级。

## 验收标准与本轮边界

自动化至少覆盖版本一致通过、主应用/安装器任一派生版本不一致被拒、缺少版本或非法格式被拒、Android `versionCode` 不单调被拒，以及候选分支不触发发布步骤。CI 对同一测试提交产出两个标注相同版本与 SHA 的 Artifact；正式晋级演练必须证明单端失败不会移动公开指针。

本轮先实现版本校验与双端候选构建门禁，不自主触发正式发布。PC 安装应等到其候选包构建、核验并完成桌面基础启动检查后再建议用户操作；远程指令能力仍按稳定启动 → 可信配对 → 只读执行顺序交付。A4 真实双端验收状态不会因统一版本号而自动改变。
