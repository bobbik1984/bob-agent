# Work 手机端项目折叠视图设计

> 日期：2026-08-11
>
> 状态：交互方向已确认，等待书面规格复核
>
> 范围：原生手机端 WorkView 信息架构；不改变桌面端项目切换、Work Core 或 Goal Runtime 数据契约

## 1. 问题

当前手机端 Work 页面仍沿用桌面式项目详情结构：页面先显示口号式标题和新建按钮，再显示单个项目或巨型空状态。它与设置、日程和知识页已经形成的“顶部同级功能 Tab + 中间内容”结构不一致，也要求用户先选择项目，再进入目标、任务、决策等内容。

手机端更适合先按信息类型切换，再在中间滚动区域连续查看所有项目。项目不是第二套页面导航，而是每个功能 Tab 内的内容分组。

## 2. 设计结论

原生手机端 WorkView 采用以下结构：

```text
WorkView（不整体滚动）
├─ 固定功能 Tab：概览｜目标｜任务｜决策｜动态
└─ 中间滚动区域
   ├─ 项目数量与“新建”动作
   ├─ 未归属或待确认内容（仅存在时）
   ├─ 项目 A 折叠分组
   ├─ 项目 B 折叠分组
   └─ 项目 C 折叠分组

App 级底部主导航保持不变
```

- 删除手机端的口号、说明性副标题和独立项目下拉选择器。
- 顶部 Tab 固定在 WorkView 顶部；App 底部主导航保持原有固定位置。
- 只有顶部 Tab 与底部导航之间的项目内容区域纵向滚动。
- 项目按最近更新时间降序排列，最近使用的项目优先出现。
- 桌面端继续使用现有单内容流和横向项目切换，不迁移为手机端折叠视图。

## 3. 功能 Tab

| Tab | 每个项目展开后显示 | 项目收起时的数量 |
|---|---|---|
| 概览 | 当前阶段、状态、下一步、待确认、最近进展 | 优先显示 `2 目标 · 5 任务`；空间不足时显示目标、任务、决策与风险数量之和，例如 `10 项` |
| 目标 | 目标、Goal Runtime 状态、审批与继续操作 | 目标总数 |
| 任务 | 未完成任务优先，其后为已完成任务 | 未完成任务数 |
| 决策 | 决策结论、理由和必要的重访条件 | 决策总数 |
| 动态 | 该项目最近活动，按时间倒序 | 当前已加载的活动数 |

顶部 Tab 是唯一的信息类型导航。概览内不得再次放置“目标、任务、决策、动态”的快捷入口。

切换 Tab 时保留各项目的展开状态，避免用户在对照不同信息类型时反复展开项目。

## 4. 项目折叠分组

### 4.1 标题行

整个项目标题行都是展开/收起按钮，结构固定为：

```text
状态圆点 + 项目名称 + 当前 Tab 的内容数量 + Chevron
```

- 状态圆点只表达项目状态：进行中使用主题色实心圆，非活跃状态使用未激活色空心圆。
- 项目名称单行截断，不因长名称增加标题行高度。
- 数量使用次级文字，不使用彩色徽章，不与项目名称争夺注意力。
- Chevron 只表达展开状态，展开时向上，收起时向下。
- 标题行提供 `aria-expanded`，并可通过键盘激活。

### 4.2 展开规则

- 每个项目独立展开或收起。
- 展开一个项目不会自动收起其他项目；用户可以同时展开多个项目进行全盘比较。
- 初次进入 Work 页时，默认展开最近使用的项目，其余项目收起。
- 当前页面会话内保留展开状态；本轮不写入数据库或全局配置。
- 切换 Tab 后沿用相同的展开项目集合。

### 4.3 展开内容

- 展开区域不再嵌套大卡片，通过分隔线、间距和短标题建立层级。
- “下一步”最多突出一项；其余内容进入对应功能 Tab。
- 待确认内容只在确实存在时出现，并提供明确动作。
- 每个项目内部的新增、继续、确认等动作复用全局按钮语义，不建立手机端专用配色。

## 5. 全局待处理内容

现有待归属内容可能尚未属于任何项目，不能强行放入项目折叠区。

- 当 `pendingLinks`、`pendingChangeReviews` 或延期复核存在时，在项目列表之前显示一条紧凑的“待处理”行和总数量。
- 点击后在同一中间滚动区域展开现有确认控件。
- 没有待处理内容时完全隐藏，不保留空白占位。
- 该区域不是新的顶部 Tab，也不改变现有确认、忽略、接受、拒绝和延期行为。

## 6. 空状态与新建项目

- 没有项目时，保留顶部功能 Tab，并在中间区域显示一条克制的空状态和唯一“新建”动作。
- 不显示品牌水印、口号、功能解释或巨型空状态边框。
- 已有项目时，中间区域顶部显示项目数量和紧凑“新建”动作。
- 新建项目继续复用现有创建表单和数据流程，只调整入口位置与移动端排版。

## 7. 数据流与性能

手机端需要同时显示所有项目的数量和展开内容。实现继续使用现有接口，不增加数据库表或客户端依赖：

1. 调用 `listProjects` 获取项目列表。
2. 按项目调用现有 `getProjectAggregate(projectId)`，使用 `Promise.allSettled` 聚合结果。
3. 将成功结果保存到以项目 ID 为键的内存 Map；单个项目加载失败不阻断其他项目。
4. 活动、任务状态或项目内容发生变化时，只刷新受影响的项目聚合；项目创建或删除后重新获取项目列表。
5. 项目列表按 `updatedAt` 倒序展示。

这些调用只访问本地 Tauri/SQLite 数据，不触发大模型、网络请求或额外运行时。

## 8. 加载与错误状态

- 首次加载时使用与项目标题行同高度的简洁骨架，不显示整页加载动画。
- 单个项目聚合失败时仍显示项目标题，数量位置显示“加载失败”，展开后提供“重试”。
- 全部项目加载失败时显示一条页面级错误和“重试”，顶部 Tab 与底部主导航保持可用。
- Tab 切换和项目展开不触发新的大模型调用。
- 用户操作失败继续使用现有可读错误信息，不暴露 IPC、SQLite 或 Rust 内部术语。

## 9. 响应式与可访问性

- 新信息架构仅由 `terminalKind === 'native-mobile'` 启用，不用页面私有像素断点决定产品模式。
- Android 横屏仍使用手机端功能 Tab 与项目折叠结构。
- 中间滚动区域使用动态可用高度和底部安全区，不使用固定 `100vh`。
- 功能 Tab、项目标题和动作按钮均使用原生 `button`，保持可见焦点和自然 Tab 顺序。
- 所有图标使用 Lucide，禁止 Emoji。
- 新增用户可见文字同步写入 `zh-CN.json` 和 `en-US.json`。
- 明暗主题只使用现有语义化 CSS 变量。

## 10. 组件边界

为避免继续扩大 `WorkView.vue`，手机端展示拆为边界清晰的组件：

- `WorkMobileTabs`：只负责活动 Tab 和切换事件。
- `WorkProjectAccordion`：只负责一个项目标题、数量、展开状态和内容插槽。
- `WorkMobileOverview`：只负责概览字段排列，不请求数据。
- `WorkView`：负责获取数据、缓存聚合、处理项目创建和业务动作。

组件不得直接调用 `window.electronAPI`；所有数据和动作通过 props/emits 由 `WorkView` 统一编排。现有桌面布局继续留在 `WorkView`，共享业务方法和聚合数据，不复制业务逻辑。

## 11. 验收标准

- 原生手机端不再显示“持续工作核心”“让复杂工作不断线”等口号式页头。
- 手机端顶部稳定显示五个功能 Tab，底部主导航保持不变。
- 页面滚动只发生在中间内容区域。
- 所有项目按更新时间排列，并在每个 Tab 内以同一折叠标题结构出现。
- 项目标题整行可展开/收起，多个项目可以同时展开。
- 收起项目显示当前 Tab 对应的内容数量。
- 切换 Tab 后保留项目展开状态。
- 概览不重复出现顶部五个功能入口。
- 单个项目加载失败不影响其他项目浏览。
- 桌面横向和桌面纵向布局不发生行为回归。
- 中文、英文、亮色、暗色和 Android 横屏均通过视觉检查。
- `npm test` 与 `npm run build` 通过，不新增 npm、Cargo、Python、MCP 或客户端运行时依赖。

## 12. 非目标

- 不改变 Work Core、Goal Runtime、同步、日历或记忆数据契约。
- 不新增项目排序、置顶、搜索、筛选或拖拽重排。
- 不把展开状态持久化到数据库。
- 不重写桌面端 Work 信息架构。
- 不升版本、不发布、不推送，除非用户另行授权。
