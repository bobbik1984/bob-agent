# Bob 统一信息与知识生命周期设计

> 状态：已确认设计
> 日期：2026-08-10
> 范围：信息捕获、自动分流、笔记、项目、知识库、知识图谱、记忆与做梦
> 不包含：本设计阶段不迁移真实数据、不改变现有运行代码

## 1. 目标

Bob 应让普通白领只负责表达和提供材料，而不需要判断内容应存放在哪个模块。系统自动把输入转化为速记、笔记、待办、日程、项目记录、知识来源或可复用知识点，并保持来源可追溯、处理可恢复、结果可迁移。

核心原则：

- Markdown 是可迁移知识的真相源，其他 Agent 无需 Bob 数据库也能理解和使用。
- SQLite 是 Bob 的运行状态、搜索、同步和图谱加速层，可以从 Markdown 重建。
- 同一对象只保留一个权威版本，通过引用进入不同视图，不通过复制文件实现分类。
- Bob 主动整理足够完整的内容；用户不承担日常分类和逐条确认负担。
- 收藏外部内容表示兴趣，不自动表示用户认同作者观点。
- 所有自动处理保留原始输入、证据、生成关系和可恢复历史。

## 2. 产品概念边界

当前界面的“速记、笔记、项目、知识库、知识图谱”不属于同一分类维度：

| 概念 | 本质 | 产品定位 |
|---|---|---|
| 速记 | 捕获入口与未成熟状态 | 灵感、随想和低置信度输入的安全收件箱 |
| 笔记 | 面向用户的完整内容 | 用户思考、会议记录、方案和 Bob 自动整理的成熟内容 |
| 项目 | 工作上下文 | 聚合项目笔记、任务、日程、来源、知识和实体的组织方式 |
| 知识库 | 外部证据与可复用知识 | 来源材料、概要、知识点、领域和主题的统一入口 |
| 知识图谱 | 展示和探索方式 | 同一批对象及关系的图形视图，不拥有另一套正文 |

系统内部使用七类基础对象：

- `Capture`：原始输入与处理过程。
- `Source`：文章、网页、PDF、文件等外部来源。
- `Note`：用户可阅读和编辑的完整内容。
- `KnowledgePoint`：有证据、可单独复用的原子知识。
- `Project`：白领工作的上下文容器。
- `Entity`：人物、组织、项目、地点和概念。
- `Memory`：关于用户、项目和 Bob 工作方式的长期有效认知。

## 3. 数据权威

### 3.1 Markdown 真相源

以下长期认知资产必须写入 Markdown：

- 来源正文、来源链接和完整性状态；
- 完整笔记及其唯一项目归属；
- 原子知识点及证据引用；
- 项目说明、项目记录和关键决策；
- 实体说明、别名和消歧信息；
- 用户确认或稳定形成的长期记忆；
- 关键关系、修订历史和废弃关系。

每个长期对象必须在 frontmatter 中包含稳定 ID。文件名和路径可以改变，稳定 ID 不变。

```yaml
---
id: kp_01JXYZ
schema_version: 1
type: knowledge_point
title: 城市动线可以转化为稳定商业客流
domains: [商业地产]
topics: [客流运营, TOD]
source_refs: [src_01JABC]
project_id:
status: active
confidence: 0.84
created_by: bob
created_at: 2026-08-10T10:00:00+08:00
updated_at: 2026-08-10T10:00:00+08:00
---
```

### 3.2 SQLite 加速层

SQLite 负责：

- Capture Journal 和处理状态；
- 全文及语义检索索引；
- 图谱节点和边缓存；
- 多端增量同步；
- 去重候选与状态筛选；
- 活动日志和界面统计；
- 自动任务的重试与恢复。

设备活动日志只保留最新 50 条。SQLite 丢失后，Bob 必须能从 Markdown 重建长期知识、搜索索引、领域视图和知识图谱。

## 4. Markdown 目录

```text
bob.agent/
├─ notes/
│  ├─ quick/                 # 速记原文
│  ├─ topics/                # 通用完整笔记
│  ├─ projects/<project-id>/ # 单一项目所属笔记
│  └─ assets/                # 笔记附件
├─ wiki/
│  ├─ sources/               # 外部来源
│  ├─ knowledge/             # 原子知识点
│  ├─ entities/              # 人物、组织、项目、地点、概念
│  ├─ memories/
│  │  ├─ user/               # 用户偏好与稳定背景
│  │  ├─ project/            # 项目决策与约束
│  │  ├─ procedural/         # Bob 可复用的工作经验
│  │  └─ corrections/        # 用户对 Bob 错误的纠正
│  ├─ sessions/              # 冷对话摘要
│  ├─ collections/           # 可重建的领域和主题聚合页
│  └─ system/                # schema、迁移清单、旧路径映射
└─ bob.db                    # 可重建索引与 Bob 运行状态
```

约束：

- 通用笔记的 `project_id` 为空；项目笔记只能属于一个项目。
- 来源默认属于领域和主题，不从属于项目，但可被任意项目引用。
- 知识点可被多个笔记和项目引用。
- 聚合页和图谱只保存引用或派生索引，不复制正文。
- 图片使用专用资源目录和可追溯命名；PC 原始文件继续使用原位置引用。

## 5. 统一信息生命周期

```text
用户输入
  → 可靠捕获
  → 意图与内容识别
  → 对象生成
  → 提炼、查重与关联
  → Markdown 提交
  → SQLite 索引、图谱与同步
  → 检索、写作、问答和 Goal 使用
```

### 5.1 输入入口

所有入口进入同一 Capture 管线：

- 悬浮窗速记；
- PC 与 Android 聊天；
- Android 系统分享；
- 网页和微信公众号链接；
- PDF、Word、文本和图片；
- 文件或文件夹拖拽；
- 对话中形成的重要结论。

Capture Journal 保留原文、来源设备、入口、内容哈希、处理状态、错误阶段、重试信息和派生对象引用。

### 5.2 高置信度自动分流

| 识别结果 | 自动动作 |
|---|---|
| 明确待办 | 创建待办 |
| 明确时间安排 | 创建日程 |
| 随想、灵感、不完整观点 | 保留速记 |
| 完整独立思考 | 创建通用笔记 |
| 明确项目工作内容 | 创建该项目下的笔记或记录 |
| 收藏文章、网页、PDF | 创建知识来源 |
| 无法可靠判断 | 留在速记 |

一次 Capture 可以生成多个对象。任何自动分流都不能覆盖或删除原始输入。

### 5.3 速记成熟

Bob 主动执行：

- 单条速记足够完整时直接生成笔记；
- 多条速记形成稳定主题时自动创建完整笔记；
- 新内容补充已有主题时更新权威笔记；
- 新旧观点冲突时并列保留并建立观点变化关系；
- 已沉淀速记标记为完成但暂不删除；
- 自动整理直接生效，并用非打扰通知告知用户。

## 6. 来源与知识提炼

外部来源按以下顺序处理：

1. 建立来源身份并保存原始链接或文件引用；
2. 提取和清洗正文；
3. 标记正文为 `complete`、`partial` 或 `failed`；
4. 生成标题、概要和主要观点；
5. 判断领域与主题；
6. 提取多个候选知识点；
7. 提取实体；
8. 与现有来源和知识点查重；
9. 原子写入 Markdown；
10. 更新 SQLite、图谱和跨端同步状态。

知识点必须：

- 只表达一个可独立复用的结论；
- 反向引用原始证据；
- 标明事实、作者观点、案例经验、Bob 推论或用户观点；
- 包含领域、主题、置信度和状态；
- 可以汇聚多个证据；
- 不能因为被项目或笔记引用而复制文件。

## 7. 知识库体验

知识库首页沿用 iKnow 易理解的卡片模式，默认展示：

- 标题；
- 一句话领域定位；
- 主要内容概要；
- 少量主题标签；
- 来源和日期。

详情页默认顺序：

1. Bob 提炼的概要；
2. 可复用知识点；
3. 用户批注和自己的思考；
4. 相关来源、笔记、项目和实体；
5. 折叠的完整原文。

普通用户无需看到内部对象类型和文件路径。知识图谱与卡片、搜索、项目页共用同一对象 ID 和关系。

## 8. 记忆与做梦

做梦机制不再无条件向 `wiki/learned` 追加碎片文件，而是：

- 合并重复知识点和证据；
- 将成熟速记自动编织为笔记；
- 发现来源之间和跨领域的方法论联系；
- 识别用户观点变化；
- 更新用户兴趣证据与置信度；
- 降低过时记忆置信度；
- 将项目决策、纠错和工作经验写入对应记忆类型。

外部收藏只能形成兴趣证据。只有用户明确表达、主动编辑、反复采用或确认后，才能提高为用户观点或稳定偏好。

## 9. 去重与版本

去重顺序：

1. 稳定 ID 相同：合并为同一对象的新版本；
2. 来源 URL 或原始文件哈希相同：不重复创建来源；
3. 正文哈希相同：识别为完全副本；
4. 语义高度相似：进入合并判断，不直接删除。

知识点合并规则：

- 相同结论、相同证据：合并；
- 相同结论、不同证据：保留一个知识点并增加证据；
- 相反结论：并列保留并建立 `contradicts`；
- 新知识替代旧知识：旧项标记 `superseded`。

## 10. 失败语义与恢复

处理过程必须区分：

- 捕获失败；
- 正文提取失败；
- 内容不完整；
- 分类失败；
- 知识点提取失败；
- Markdown 写入失败；
- SQLite 索引失败；
- 图谱更新失败；
- 多端同步失败。

恢复规则：

- Markdown 成功、SQLite 失败：知识安全，后台重建索引；
- SQLite 成功、Markdown 失败：不得标记长期知识提交成功；
- 摘要成功、正文不完整：来源标记 `partial`；
- 分类失败：进入“未分类”，不能丢失；
- 做梦整理失败：保留原始速记并在下次重试。

## 11. 现有数据迁移

现有数据反映了多个历史机制，不直接原地清理。迁移流程：

```text
只读扫描
  → 迁移报告
  → 可恢复归档
  → 分配稳定 ID
  → 写入新结构
  → 重建 SQLite
  → 校验数量、引用和召回
  → 切换读取路径
  → 保留旧路径映射
```

映射规则：

- `wiki/sources`：保留并补充稳定 ID；
- `notes/topics`：保留真正的用户笔记；
- 完全相同的跨目录文件：选择一个权威对象，其他位置变为映射或归档；
- `wiki/learned`：分别迁移到 `wiki/knowledge` 或 `wiki/memories`；
- `wiki/projects`：转换为项目聚合视图；
- `wiki/entities`：消歧后继续使用；
- `wiki/sessions`：继续作为冷对话摘要；
- `wiki/index.md`：从新结构重建。

迁移必须幂等。单个文件失败不阻断其他文件，失败项进入隔离清单。完成验证前不永久删除旧文件。

## 12. 测试与验收

### 12.1 单元测试

- Capture 分流；
- 稳定 ID 与 frontmatter；
- URL、文件哈希和正文哈希去重；
- 笔记的单项目归属；
- 来源、知识点和证据引用；
- 冲突观点和版本替代；
- Markdown 原子提交；
- SQLite 从 Markdown 重建。

### 12.2 端到端测试

1. 悬浮窗记录灵感；
2. 多条灵感自动形成完整笔记；
3. 明确待办进入待办；
4. 明确安排进入日历；
5. 收藏 Eaton Centre 微信文章；
6. 从文章生成多个商业地产知识点；
7. 再次收藏同一文章不产生副本；
8. 项目笔记引用通用来源；
9. PC 与 Android 同步后对象 ID 一致；
10. 删除 SQLite 后重建搜索和图谱。

### 12.3 迁移验收

迁移前后核对：

- 文件总数和权威对象数；
- 完全重复和近似重复候选；
- 失效引用和未分类文件；
- 索引和图谱对象数；
- 来源原文可访问性；
- 知识点证据可追溯性；
- 项目笔记归属；
- 旧内容搜索召回率。

### 12.4 产品验收

用户可以：

- 随手输入而不考虑存储位置；
- 收藏资料后看到标题、概要和领域；
- 先阅读知识点，再展开原文；
- 搜索领域时同时获得来源和可复用知识；
- 在项目中引用通用知识而不产生副本；
- 在图谱中查看同一批对象；
- 用其他 Agent 直接读取 Markdown；
- 在 Bob 数据库损坏后恢复长期知识。

## 13. 实施顺序

1. 定义 Markdown schema、稳定 ID 和关系词表；
2. 建立只读扫描器和迁移审计报告；
3. 建立可重建 SQLite 派生索引；
4. 统一 Capture 自动分流；
5. 改造来源提取和知识点生成；
6. 实现速记自动成熟和笔记更新；
7. 改造知识库卡片和详情页；
8. 让知识图谱读取统一对象；
9. 改造记忆与做梦写入规则；
10. 迁移现有真实数据；
11. 验证 PC、Android 和索引重建；
12. 归档旧目录。

## 14. 非目标

- 不引入 Python 或新的客户端运行时；
- 不让普通用户管理知识对象、DAG 或数据库；
- 不在第一阶段自动永久删除历史文件；
- 不把所有收藏内容当作用户观点；
- 不为了图谱展示复制 Markdown；
- 不在本设计阶段改变 Goal Runtime。
