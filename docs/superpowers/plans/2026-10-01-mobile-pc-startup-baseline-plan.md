# Bob 手机→PC 重建：S0/S1 实施计划

依据：[稳定启动基线设计](../specs/2026-10-01-mobile-pc-rebuild-startup-baseline-design.md)。本计划只管稳定启动；可信配对和只读执行另立施工单。当前施工线从 `a896f53` 建立，不按 v0.9.16～v0.9.21 顺序合并。

## S0：基线与可恢复锚点

1. 保留原诊断分支和当前手机安装数据；独立工作树 `mobile-pc-rebuild` 从 `a896f53` 建立。记录工作树 HEAD、原始 APK 文件大小与 SHA-256、签名证书指纹。
2. 核对原始 APK 是否确实由 `a896f53` 对应版本构建；无法建立构建来源对应关系时标为“版本标称相符，来源未证实”，不得写成精确可复现。
3. 在不覆盖当前手机数据的前提下规划 v0.9.15 真机复现方式。若无法安全并存安装，停止设备操作，仅保留用户过去成功运行的历史事实，不称作当前环境复测通过。
4. 记录 v0.9.15 现有启动依赖清单：HTML/JS 顶层模块、`App.vue` 挂载前与挂载后行为、Bridge 顶层监听、Rust `setup()`、数据库初始化和网络任务。标出同步 await、无界等待、密钥与网络操作的位置。

S0 输出：脱敏基线证据、启动调用图、首个最小修改集；不更新 `progress.yaml` 为完成。

## S1：最小首屏隔离

1. 为前端入口加入最小阶段探针，记录入口求值、Vue 挂载前后、首屏可交互；阶段码不得包含用户内容、令牌或完整文件路径。诊断探针默认不产生大量日志。
2. 将对首屏非必要的 Bridge 监听注册与协同初始化推迟到根视图成功挂载之后；每项异步任务独立捕获错误并显示协同不可用状态。保留原有用户功能，不以吞错替代修复。
3. 使本地配置和已配对状态加载具有可见的失败状态；不得用“定时强制删除 Logo”作为启动通过判据。若 Vue 挂载失败，留下诊断信息而非显示一个空白聊天页。
4. 定位并拆出 S1 涉及的最小单元与测试接缝，避免扩写巨型 `App.vue` 的启动职责；不改无关票夹、图谱、模型选择或远程写入逻辑。

## 自动化验证门槛

- 前端测试直接调用生产启动状态转移单元，覆盖无配对、已配对但 PC 离线、配置错误、同步挂起、未知回执、重复启动以及错误晚到事件。测试不得复制一份手写状态机。
- Rust 检查启动时任务为后台启动、错误可观察；不把进程存活等同于 UI 可用。若改动 Rust，补正常与异常路径测试。
- 运行相关 Vitest、Rust targeted tests、静态检查与 `git diff --check`；记录实际命令、退出码和测试数。构建或真机安装须另行满足重型操作与数据保护门禁。

## 真机 S1 出口门槛

同一候选包分别在未配对和已配对状态下完成冷启动、结束进程后重启、无网、PC 离线，并且每次都进入能操作的界面。需要记录构建 SHA、APK 哈希、签名、设备/Android 版本、耗时与最后阶段码。只有静态 Logo 或只有 Android 进程存活一律失败。任何凭据泄漏、用户数据丢失或要求卸载清数据时立即停止。

本地测试通过只表示 S1 实现候选，不解锁后续 S2 或 A4 真机门禁。
