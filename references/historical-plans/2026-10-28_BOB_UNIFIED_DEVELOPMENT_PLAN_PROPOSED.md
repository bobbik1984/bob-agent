# Bob 统一产品架构与完整开发路线

> 日期：2026-10-28  
> 状态：PROPOSED，产品方向已明确，目标架构和实施路径待现场核实与审阅。  
> 用途：统一产品思路，为能访问真实开发环境的 Agent 提供有依赖、有验收门的开发路线。  
> 边界：本次交付规划，不执行归档、代码变更、迁移或发布。

## 1 一页结论

**Bob 是一个用户自己的、开源、BYOK 的个人助理。手机 Bob、PC bob-agent 与 online-agent 是它的不同使用形态，不是要拼在一起的几个远程编程工具。** 统一的重点是：容易开始使用，事情做了一半能继续，成果和决定能找回，并能接入不同设备、模型与工具。

“同一个 Bob”不依赖一个永不结束的模型 session。它依赖稳定的事项身份、可追溯的材料和成果、明确的决定、授权及恢复状态。用户可以关闭页面、换设备、换 Agent，仍知道事情做到哪里、下一步是什么；远端不可用时也能知道哪些能继续、哪些必须等待。

两个现有子项目应朝这个方向发展，但**现有实现不自动等于最佳实现**。要保护的是用户价值、数据资产、历史证据、有效能力和合理的使用习惯，不是技术债。现有模块可以保留、适配、替换、合并或退役；每项选择都要有场景收益、现场证据和可回退的理由。Bob App 的现有设计语言是体验基准，不是所有现有组件必须保留的技术裁决。Online 的任务与成果治理融入同一体验，不另做一套竞争界面。

建议按以下顺序推进：**愿景与场景 → 真实盘点 → 全局架构校准 → 目标架构与替换决策 → 仓库组织 → 经批准的保护与小闭环 → 渐进迁移 → 可靠性、易用性与发行。** 多仓库联合开发可以是保守起点；monorepo 必须在架构校准之后决定。不要用搬目录代替产品和架构设计，也不要用“全部重写”绕开已有资产。

Online 仍应能独立好用、独立自部署，App 也应独立推进；两者接入不是彼此可用的前置条件。基本个人助理使用不应强迫用户先架服务器。统一产品也不要求统一所有构建、版本号或发布节奏。

**首次开发 Agent 只交付现场盘点、产品与架构冲突、目标方案选项、可恢复基线提案，然后停在审阅门。完整路线不等于实施授权，复制备份也不能先做。**

## 2 哪些已确定 哪些仍需核实

### 已确认的用户方向

- 两个现有子项目统一为一个开源、BYOK 的个人助理；从使用便利、连续性和可扩展性重新思考，而不只是整理仓库。
- 保留有价值的能力和资产，但允许重审实现；架构和代码组织不能只因“已经这样写了”就冻结。
- 当前任务是重整思路和开发路径，不授权实施、生产变更或新的对外访问权限。

### 已读共同愿景与路线中的目标

共同愿景将 Personal Assistant 定为产品身份，将 Universal Work Access 定为真实工作能力：Bob 是随处可用的入口，不是唯一 UI；原生 IDE 或 Harness 可以继续使用。结构有用时才出现，日常捕获不必每条消息都创建 Task，助理与专注模式共享身份语义。

共同愿景强调 Kernel owns truth、Providers provide capabilities、Recipes compose work。普通内部组件正常组织；只有真实替换点才需要 Provider/Adapter，出现第三方生命周期、权限和版本治理需求时才考虑 Plugin。上下文有界、可溯源、可纠正、可遗忘；向量库、自动路由和广泛多 Agent 编队都不是基础体验的前置条件。这些是文档目标，不是已实现声明。

## 3 产品应如何被使用

### 旅程一 先成为好用的个人助理

目标是用户安装或打开受支持的 Bob 入口后，添加自己的 Provider，即可开始基本对话、处理已授权材料和使用平台允许的文件能力，不必先理解 Core、Host、Harness 或自架服务器。首屏优先回答“你想做什么”，不是要求填完整拓扑图。权限或 Provider 不可用时给出具体原因与最小下一步，不默默换模型、换主机或扩大权限。

无服务器不等于离线。远程 BYOK 模型仍需要网络；离线只承诺经过验证的捕获、缓存和已有本地工具。网页、手机和桌面受操作系统权限影响，不能承诺所有平台都能任意读写本地文件。

### 旅程二 从手机处理电脑上的普通文件

早期非编程验收采用明确路径：**手机请求读取指定 PC Workspace 中的指定文档 → 查看简短总结 → 用户批准后导出成果。** 选择 PC 是选择执行位置，不等于选择本地模型。普通用户看到可信设备、可访问材料和操作范围；高级用户再展开 Harness/Profile。远端离线时显示等待或不可用，不能假装任务已经迁到手机执行。

原生编程 Harness 是另一条能力路径，不用它通过一条 coding 测试就代表通用 Work 已完成。Chat 和 Work 都可以使用获准工具；Chat 不是“没有工具”，Work 也不是“只能编程”。

### 旅程三 事情变复杂时再进入 Work

随手问答、记录想法不强制生成项目和任务。需要持续推进、版本成果、反馈或审批时，才将事项渐进提升为 Work，保留原 conversation、材料、决定和 artifact 引用。提升改变组织方式，不自动扩权，也不重新生成一个失去上下文的同名任务。

用户可在同一事项中继续补材料、检查成果、指出问题并生成后续版本。Project、Workspace、Host 分开：项目可以引用合适设备上的工作空间，而不是要求把全部文件搬到统一云盘。“同一件工作”不等于“同步全部文件”。

### 旅程四 离开和回来都不丢状态

切换设备、关闭页面、短暂掉线后，应恢复有授权的历史、草稿、材料引用、审批上下文和阅读位置。界面必须区分本地保存、等待发送、服务端已接收、排队、执行中、结果待核验和状态未知。未收到确定回执不能显示已接收；`unknown-send` 不能直接当成失败再发一次。

先把单写者、明确交接和可解释冲突做好，再考虑复杂多端编辑合并。远端未连接时可以保存草稿或待办，但排队是否允许、何时会发出必须清楚，不能在恢复连接后执行过期或已撤销的意图。

### 旅程五 继续已经在原生工具里做的工作

用户可继续使用原生 IDE、CLI 或其他 Harness。Bob 先展示真实可用的会话和能力，在明确授权后关联原 Project/Task、Host/Workspace 和进度资料。换 Harness 时记录新的 Execution 和来源，保留已有任务身份；这不意味着搬迁正在运行的进程、永久续用模型 session，或自动迁移全部聊天历史。

原会话仍有活动写者、发送状态不明或映射不可靠时，不争抢执行。支持 native resume、steer、cancel 与否逐 Harness 标明，不能用“已连接”掩盖能力差异。

### 旅程六 有需要时再加常驻服务

用户按需要自部署 Online，取得常驻工作治理、设备协调、授权范围内的历史访问、备份或提醒能力。这是可选增强，不是第一次使用的门槛。备份策略、提醒和常驻执行仍需具体配置与授权，不因启用 self-host 就默认读取所有文件或替用户发送消息。

便利性应来自有效策略继承和渐进展示：项目已有合法的模型、主机和权限选择可以沿用，用户只确认本次变化；详情随时可查看。策略失效或能力改变时重新解释，不以静默 fallback 换取表面顺畅。

## 4 目标架构候选

以下是待校准的逻辑划分，不是冻结的服务、目录或技术栈。全局检查后可以调整边界，不能先照此建包再寻找理由。

### 4.1 五层职责

1. **多端 UI 与 Shell。** 手机、桌面、网页采用一致的身份、操作和状态语言，适配各自输入、文件与系统能力。以现有 Bob UI 设计语言校准体验，不强制复用不合适的组件；Online 的治理能力进入同一界面结构。
2. **个人连续性与领域层。** 管理 conversation、材料引用、决定、渐进形成的 Work，以及有界上下文。它回答“这是什么事情、为什么这样做、下一步是什么”，不承诺模型内部 session 永久存在。
3. **工作状态与治理层。** 管理明确归属的 Project、Task、Execution、Artifact、Verification、Review、批准和操作回执。Kernel owns truth 指这里的权威原则，不代表所有本地事项必须先上传一个云端服务。
4. **执行协作层。** 在授权 Host、Workspace、Harness 上协调执行、交接、取消、进度和错误恢复。能力矩阵与协议应保留真实差异，不用一个通用接口伪装所有 Harness 都支持相同行为。
5. **资源 Provider 与平台适配层。** 接入模型、文件、设备能力、凭据存储和必要外部服务。Recipes 组合已获准的能力，不创造新的权限；普通内部模块无需包装成 Plugin。

### 4.2 先确定每份数据由谁写

基本 standalone 模式应可以独立运行，不要求每次对话或本地 Task 都先进入云 Core。但当前已连接 Online 工作仍遵守 Core 单写规则；本地领域保留明确 owner 与 namespace，不能在 App 再造一份可写 Online Work 真相。

跨来源引用、关联、import 或 owner 转移必须分别设计：原始 ID、来源 owner、稳定版本、映射关系和 provenance 都要可追踪；不能按名称合并。是否只引用、何时复制、何时转移写入权，以及断线时哪些操作可做，需要独立批准和兼容方案。先采用单写者与明确交接，复杂离线冲突合并不是首轮前置。活动数据库不能通过文件同步成为跨端“共享状态”。

Native session、Local Work、在线工作和外部文件的原始证据保留各自归属。领域抽象可以提供统一入口，但不能压平来源差异，删掉原始回执或把引用伪装成已托管的成果。

### 4.3 运行身份 授权和数据去向

Host 是执行主机；Harness 是运行 Agent 的方式；Workspace 是文件与工作边界；Provider 是能力来源；Profile 是可选择的运行配置。Project 不等于以上任一项。界面应让用户知道本次在哪执行、访问哪些材料、内容发往哪个 Provider、成果存在哪里。

配对身份、操作授权、Provider 认证是三个域。配对成功不代表可以写文件，配置了模型 key 不代表批准执行。凭据优先留在适用平台的安全存储或获准执行主机，按最小必要范围引用；浏览器端需单独评估其存储安全，不假定有原生安全库。不能为“跨端方便”同步所有密钥或把 secrets 放入日志、成果、同步状态和普通备份。

模型字段区分 Requested、Resolved、Observed：用户请求什么、配置解析到什么、实际证据观察到什么。没有实际观测就保留 `unknown`；不能拿配置值填充实际值。主机、模型或权限的 fallback 必须符合用户明确策略，不能默认静默切换。

### 4.4 输入输出与上下文契约

输入至少表达用户意图与正文、材料引用、目标身份、期望父版本、授权范围和操作 ID；接收端给可关联回执。输出区分进度事件、批准请求、正式成果版本、行为验证、人工审阅和错误证据。重试应能识别同一意图而不重复执行；发送结果未知时有查询与对账路径，而不是直接重放。

契约需有版本和兼容策略，保持原始事件及证据可追溯。正式 Artifact 要能验证父版本、内容 hash、来源 Execution、存储位置和可读性；“进程退出成功”不等于“成果正确”。临时文件、已登记成果、已核验成果和用户接受的成果不要混成一个 completed。

上下文先解决来源、有效范围、预算、纠正、遗忘和跨项目权限，再决定检索实现。用户纠正不能只是追加一条永远无法覆盖的记忆，遗忘也不能只隐藏 UI 却继续注入模型。具体保留与删除语义需结合审计及数据政策设计。向量库、自动路由、编队和插件市场都须由已验证需求驱动。

## 5 完整开发路径与依赖

步骤不是工期承诺。A 可先在纸面开展；B 得到现场事实后才可完成 C。D、E 的选项可以预研，但正式选择必须经过 C、D 的相应审阅。F 之后的测试与回滚贯穿每一步，不等到 H 才补可靠性。

### 步骤 A 校准愿景和代表性场景

**目标与输入：** 将共同愿景、两仓原始愿景、用户本轮方向和现有使用体验对齐，明确不是远程 coding 工具拼装。

**动作与输出：** 建立“原始意图—用户场景—现有能力—差距”的地图；画出上述旅程的最少步骤、权限提示和失败状态；区分基础能力、可选增强与非目标。输出一页产品定义、场景清单及待确认冲突。

**验收门：** 手机、桌面、网页身份一致；日常捕获不强制 Task，普通文件工作和高级 Harness 都有位置。**停止条件：** 未读到原始文件时保留缺口，不声称已完成双项目原始愿景核对；方向冲突需用户裁决。

### 步骤 B 真实盘点与保护基线提案

**目标与输入：** 在已授权环境、最新合同和本地规则下，知道有什么、谁在写、哪些能恢复。

**动作与输出：** 只读盘点仓库根路径、脱敏 remotes、branches/tags/HEAD、staged/unstaged/untracked/ignored 清单、submodules/LFS/外部资产；worktree 的实际路径、注册与搬移；依赖、工具链、构建测试部署脚本及 CI；DB/schema/成果路径、数据 owner、活动任务与写者、已安装或部署制品 hash 与源码映射、历史证据与备份。读取必要元数据，不导出 secrets 或运行数据。输出事实表、差异与 unknown、代码和运行数据分离的保护方案。

**验收门：** 每项有观察时间、来源与限制；未提交资产不能遗漏，HEAD 不能代指生产。**停止条件：** 需要改环境、安装、构建、付费调用或扩大读取权限才能继续时，暂停该项。此步不复制任何备份。

### 步骤 C 全局架构校准门

**目标与输入：** 基于 A 的产品目标和 B 的实际盘点，审查整个系统，而不是只检查新旧接口能否接通。

**动作与输出：** 建立“文档宣称—代码实际—运行观察”矩阵；运行证据未获准或缺失时标 unknown，不偷偷启动服务补证。沿输入、身份、权限、数据 owner、执行生命周期、成果、错误与恢复逐段追踪。找出双重权威、重复领域模型、职责泄漏、隐式模型/主机选择和过度耦合，说明它们怎样影响真实旅程。输出全局问题图、风险排序和决策清单。

**验收门：** 用户审阅产品目标与现有边界的冲突，明确哪些约束保留、哪些允许重设；每个关键问题有证据或补证要求。**停止条件：** 关键数据所有权、授权或恢复边界仍无法说明时，不宣布架构通过，不跳到仓库迁移。

### 步骤 D 选择目标架构与组件去留

**目标与输入：** 在 C 的校准结论上形成满足场景的目标架构，而不是将现有代码位置美化成设计图。

**动作与输出：** 逐组件选择 retain、adapt、replace、merge 或 retire，写出用户收益、证据、替代选项、依赖、兼容方式和回滚。候选须覆盖 standalone 与 connected 两种模式、唯一写者、身份映射、权限及模型观测。允许更换实现；退役前保证用户资产、引用和有效行为有去处。输出目标边界图、关键 I/O 契约和带批准状态的去留表。

**验收门：** 目标方案经审阅，关键 owner 与迁移风险有解；保留和替换都有理由。**停止条件：** 只能依靠丢数据、抹历史、无界重写或第二份可写真相才能成立时，返回 C/D 比较替代方案。

### 步骤 E 再选择仓库和协作方式

**目标与输入：** 根据已审阅边界、实际跨仓修改频率和团队约束，选择组织代码的方式。

**动作与输出：** 比较联合工作区加多仓库与 monorepo 的原子修改、权限、历史、CI、许可证、共享包和发布成本。多仓库可作为保守起点，但不是永久结论；monorepo 也不能仅因“一个产品”而获选。输出选项比较、推荐、路径影响、迁移与撤回方案。

**验收门：** 仓库选择服务于目标架构，可保留独立构建、版本和发布；选择及具体迁移动作分别批准。**停止条件：** C/D 未通过、路径或来源未盘清、收益只有目录更整齐时，不移动、不合并、不重写历史。

### 步骤 F 经批准建立保护点并实现最小纵向切片

**目标与输入：** 在已批准方案、可靠恢复结果及精确实施授权下，证明统一确实改善一个普通用户任务。

**动作与输出：** 先按批准范围制作并验证保护点；未证明恢复的范围不得作为后续不可逆变更的安全依据。实施先走只读：手机访问明确授权的 PC 文档、取得简短总结并查看历史；另获受控写入批准后导出正式版本成果。加入 Chat 渐进提升 Work，保留 conversation/material/artifact 引用；后续同一 Task 经新 Execution 续接，手机和网页回看成果。高级 Harness 另列切片与批准，不能由普通路径代证。输出可复现样例、证据、限制和回滚结果。

**验收门：** 用户能完成非编程文件任务，身份和父版本一致，权限不随视图扩大，旧版本只读；请求、回执和结果可对账。**停止条件：** 恢复未过、身份不明、双写、未知发送、授权串用或来源丢失，暂停相关切片，不伪造闭环。

### 步骤 G 渐进迁移契约和共享领域

**目标与输入：** 用 F 的真实反馈与重复成本证据决定共享内容，而非启动巨大重构。

**动作与输出：** 先稳定契约、身份、错误与版本语义，再逐批抽取领域逻辑和适合共享的界面规范；兼容适配器维持旧入口。数据关联、import 和 owner 转移分开审批，明确 ID 映射、切换点、唯一写者、对账和撤回；旧历史保留可读。输出小批变更、兼容矩阵、测试与迁移记录。

**验收门：** 新旧路径有证据兼容，共享确实减少维护成本，部署仍可追溯。**停止条件：** 回归、隐式扩权、历史重写或无回滚的数据切换发生时不扩大迁移；不能为了共享而虚报各端能力。

### 步骤 H 完整成果链 连续性与失败恢复

**目标与输入：** 在 F/G 持续测试基础上，系统覆盖中断、失败及实际设备差异，不把一次成功当成产品完成。

**动作与输出：** 验证接收回执、幂等、unknown-send 对账、单写者、排队取消、断线恢复、草稿和审批恢复；验证成果父版/hash、实际可读、行为核验与人工 Review。对每个 Harness 分列能力与证据。故障注入在隔离环境进行，不破坏生产网络。输出故障矩阵、自动回归及真实设备检查记录。

**验收门：** 失败可解释，不重复执行，未确认不显示成功，历史版本不被覆盖；模拟手机视口与真实手机证据分列。**停止条件：** 无法判断是否已发送、无法确认写者、取消状态不可靠或恢复会重放副作用时保持 hold，先诊断。

### 步骤 I 完善易用性并验证扩展边界

**目标与输入：** 基于真实用户路径和 adapter 接入数据，减少摩擦而不隐藏风险。

**动作与输出：** 优化首次配置、有效策略继承、渐进详情、连接说明、错误恢复、移动输入、附件、滚动返回与可访问性。选一个真实替换点，用两种真实实现检验窄 Provider/Adapter 契约，再判断是否需要插件 SDK。只有出现第三方分发及生命周期需求，才设计安装、版本兼容、权限隔离、升级、撤销和卸载；不预建市场或 Everything Plugin 框架。输出体验修订、两实现契约结果和扩展决策。

**验收门：** 普通用户步骤减少且授权仍可理解；新 adapter 不靠私有旁路破坏数据权威。**停止条件：** 便利依赖静默换模型/主机、自动扩大权限，或扩展只在 mock 中成立时，不宣称完成。

### 步骤 J 发行 自部署与开源准备

**目标与输入：** 在关键旅程、恢复与兼容门通过后，形成别人可以安装、使用、升级和维护的产品。

**动作与输出：** 核查许可证与依赖清单，准备脱敏示例、安装和 self-host 文档、贡献指南、安全报告渠道、升级与迁移说明；验证干净环境安装、升级保留数据、备份还原与回退。公开发布前检查代码、历史、补丁和演示资产的敏感信息；发布包有来源与 hash。输出发行候选、支持范围、已知限制和可复现验收记录。

**验收门：** 基础 standalone 和获准的 self-host 路径分别可用，升级不丢资产，发布与部署按各自批准执行。**停止条件：** 隐私、许可证、权限、数据迁移或恢复存在阻塞时不发布；不能把本地验证写成已上线或真机验收。

## 6 全程护栏与批准边界

### 可恢复检查点不是放弃旧项目

归档是一个可解释、校验和恢复的里程碑，旧项目、部署、合同和证据不会因此失效。第一次只提交方案，**复制备份前必须获批范围、目的地、一致性方法和敏感排除规则**。

代码保护应覆盖 Git 历史/refs、暂存与未暂存改动、必要二进制差异、经审阅的 untracked allowlist，另列 ignored 中必要资产、LFS、submodule、外部资源、工具链、许可证、制品、证据引用、清单/hash 和恢复说明。只存 HEAD 或压缩根目录不等于完整。若历史或补丁含敏感数据，既不能以“保留历史”为由上传，也不能擅自重写；先报告类别、范围与受保护保存选项。

运行数据单独保护，明确 owner、范围、加密、密钥管理、保留期及引擎支持的一致性备份或快照。不要把活动 DB/secrets 塞入代码 ZIP，不同步活动 SQLite，不偷偷停库或改配置。隔离临时环境的恢复演练也须获批；未演练的副本只能标“已创建、未验证”。

### 实施门与暂停项

REVIEW GATE 在任何代码实施、迁移、移动、删除、改名、prune、历史重写、生产变更或新建/轮换凭据之前。设计批准不自动涵盖实施，归档批准也不涵盖后续迁移。每次批准要明确对象、范围、风险、验证、回滚和停止条件。

B4 继续 HOLD：先复核实际状态并寻找可验证的原始备份；记录路径缺失不能推断所有副本不存在。找不到则由用户决定有证据的结案，再另批受控清理。不得执行旧 finish/prune、不重建同 ID Task、不清除旧失败证据、不用新 boot 证明旧树已清理，不恢复未获批模型或其他旧任务。

决策记录统一包含：**选择、状态、证据、替代方案、可逆边界、所需批准**，并关联明确授权。状态区分 proposed、approved、verified、rejected。只有获批且有核验结果后，才更新既有 `CURRENT_STAGE`、`DECISIONS` 等权威位置；本文不接管执行队列。

## 7 用什么判断进展

先记录基线，再与用户约定目标，不虚构通过率、时长或“减少多少步骤”。建议只跟踪五类指标：

1. **续接成功且无重复执行：** 同一事项换入口、断线或交接后能否继续；重复请求是否造成重复副作用。
2. **任务启动摩擦：** 普通用户完成代表性任务需要多少配置、选择与打断，哪些是必要授权、哪些是可消除负担。
3. **阻塞状态可理解率：** 用户能否说清当前卡在哪里、是否已发送、谁需要行动、下一步怎么做。
4. **成果找回与复用成功：** 能否找回指定旧版本、验证来源、继续反馈并复用，而不误改历史。
5. **新 adapter 接入成本与契约符合性：** 真实接入需要多少特例，是否遵守身份、授权、错误和数据所有权约定。

最高优先回归保护三件事：连续性不重复且不发生无授权模型漂移；历史与旧成果只读；连接、执行、成果、Verification、Review 状态真实分层。草稿、附件、滚动返回、批准上下文、可访问性和移动端体验随每次相关变更测试。

Harness 矩阵分开记录 configured、reachable、authorized、verified，以及 native resume、steer、cancel、attachments、artifacts、events、model observation。每项有适用版本、证据和限制；未知就写 unknown。窄屏浏览器模拟不是手机真机测试，本地通过不是公网通过，另一 Harness 的成功也不是本 Harness 的证据。
